# Gmail sending: account-owner setup

No Gmail password, SMTP, third-party mail service, automatic account authorization, billing enablement, app publication or verification submission is used. Only the account owner should run the authorization helper. It is not a public website route.

1. Sign in as **ajarapmcpr@gmail.com**, open [Google Cloud Console](https://console.cloud.google.com/), and create or select a project owned by the organization.
2. In **APIs & Services → Library**, enable **Gmail API**. Do not enable billing automatically; review any Google account or organization restrictions before proceeding.
3. Open **Google Auth platform**. Configure **Branding** (app name, support/developer contact), **Audience** (External for a consumer Gmail account), and **Data Access**. Add only `https://www.googleapis.com/auth/gmail.send`. In Testing, add `ajarapmcpr@gmail.com` as a test user. Follow [Google's current consent-screen guide](https://developers.google.com/workspace/guides/configure-oauth-consent); console labels can change. Production use may require sensitive-scope verification. Do not publish or submit verification without the organization's explicit approval.
4. Under **Clients**, create an OAuth client of type **Desktop app** for the one-time local owner tool. Keep its client ID and client secret private. This helper uses Google's supported loopback/PKCE flow, not a website visitor login. See [desktop OAuth documentation](https://developers.google.com/identity/protocols/oauth2/native-app).
5. Copy `.env.example` to `.env.local`. Run `chmod 600 .env.local`, then enter the client ID and secret there. Leave `GOOGLE_REFRESH_TOKEN` empty initially. Confirm both CONTACT_FROM_EMAIL and CONTACT_TO_EMAIL equal `ajarapmcpr@gmail.com`. Set NEXT_PUBLIC_SITE_URL to your local origin (normally `http://localhost:3000`). Never paste real secrets into chat or commit them.
6. From this repository, run `node --env-file=.env.local scripts/gmail-authorize.mjs`. Open the printed Google URL yourself. Confirm the signed-in account is `ajarapmcpr@gmail.com` and grant **send only**. The helper checks state/PKCE, exchanges the authorization code and writes the refresh token directly into `.env.local` with owner-only file permissions. It prints no token. Do not share the file. The consent flow must be completed by the owner; it is never run automatically by this implementation.
7. Restart `npm run dev` so the server reads `.env.local`. Open `/contact`; its unavailable notice should disappear. If it remains, check all five server credential/address settings locally. The API refreshes a short-lived access token on the server and calls [users.messages.send](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send). No client secret, access token or refresh token enters frontend JavaScript.
8. Submit one clearly labeled test message through `/contact`, using an email you control for Reply-To. Confirm Gmail API acceptance in the UI, then separately check the organization's Gmail inbox and Reply-To behavior. Acceptance is not proof of inbox delivery. On failure the entered values remain. An ambiguous send is not automatically retried; duplicates are rejected for ten minutes within one Node process. No real email has been verified during implementation.
9. Later, in DigitalOcean App Platform component environment variables, store GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET and GOOGLE_REFRESH_TOKEN as encrypted server secrets; add the two CONTACT email settings and set NEXT_PUBLIC_SITE_URL to the real HTTPS site origin at **build and runtime**. Do not run the owner authorization helper on the public server. Configure a trusted ingress with shared rate limiting and duplicate protection before multiple instances; in-memory buckets/idempotency records are process-local and reset on restarts. Enable CONTACT_TRUST_PROXY only if that ingress overwrites X-Forwarded-For. Do not deploy until approved.

## Limitations

`gmail.send` is a **sensitive** scope, not full mailbox access; Google may require verification for production use or apply account restrictions. External apps in Testing get refresh tokens that expire after **seven days** for this scope. Testing tokens are not a permanent production solution. Tokens can also be revoked or expire after account/security changes. See [scope classification](https://developers.google.com/workspace/gmail/api/auth/scopes) and [token expiration](https://developers.google.com/identity/protocols/oauth2#expiration).

This uses Google's standard Gmail API directly without buying an email provider. It does not promise unlimited free use. Google API quotas and account sending limits still apply; see [usage limits](https://developers.google.com/workspace/gmail/api/reference/quota). No billing is enabled by the app or helper. If Google presents a billing, verification or account restriction, review it with the organization instead of bypassing it.
